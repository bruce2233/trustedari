Three questions

先回答三个"凭什么"

01

跑腿的为什么看不到我买了什么？

因为钥匙被掰成了两半，每人一半。跑腿的手里的包裹是锁着的， 加上他那半把钥匙也开不了——就像保险柜要两把钥匙同时转才能开。 每次要"看一眼里面"，两个人必须隔着桌子合力开锁 （技术上叫 2PC 联合计算：双方各出半把钥匙算一遍， 过程本身不会泄露任何人的那半把）。 所以跑腿的一路只搬得上锁的箱子，永远不知道里面是什么。

02

为什么跑腿的不能把我带去别家店？

因为验招牌的是我，不是跑腿的。每家正规商店都有一张挂在门上的 "营业执照"（证书），上面写着店名、而且无法伪造。 跑腿的要是把我带去冒牌店，我这头一看执照店名不对，立刻转身走人 （A 本地解密证书并核对域名，不匹配就中止握手—— 已实测拒绝）。跑腿的只能搬箱子，"对面是谁"他说了不算。

03

为什么账单数字没法偷偷改小？

因为账单不是谁报多少就是多少。商店给的账单封在防拆信封里， 谁碰过一眼就能看出来（GCM 防篡改）。 我报的数字跑腿的不信、跑腿的加码我也不干—— 于是两人合力把信封撕开一条缝，只露出账单那一行数字， 当场对一遍：数字、位置对不对得上 （2PC 电路里逐字节比对 + 深度校验 + com_A 承诺钉死我的那半把钥匙）。 对不上就拒付；而且整个过程账单其它内容谁也看不见。

Baselines

以前找"跑腿的"的法子，为什么都不太行

既要跑腿的不偷看，又要账单能核对——以前的办法只能占一头， 缺的其实不是加密，而是"钥匙没人独占"这个结构：

不要跑腿的，自己跑（直连）

我自己去商店当然没人偷看，但也就没人帮我盯着账单—— 用了多少 token 全靠我嘴上报，报少没人发现。

✗ 没人监督计费

把钥匙整把给跑腿的（终结代理 / CDN）

跑腿的直接替我开箱打包：他能看见一切，我买什么他一清二楚； 账单也照样是他自己报。

✗ 全被偷看

只让跑腿的搬箱子（纯转发）

他确实什么都看不见，可也什么都帮不了： 只能按箱子重量收钱，账单里的 token 数没法核对。

✗ 只能按流量计费

给跑腿的配个"保险箱"（TEE / SGX）

事情在保险箱里办、理论上都能成——但保险箱是芯片厂商做的， 得相信他们没留后门、保险箱也没被人撬开过（侧信道事故有一长串）。

△ 得额外信一台硬件

再请个"证人"陪跑（DECO / zkTLS）

思路也是钥匙掰两半，但它的目标是"证明东西真从这家店买的"： 证人得看着你递单子、知道你大概买了什么，也不负责帮你核账单。

△ 目的不同 · 单子对证人半公开

TrustedARI（本工作）

钥匙掰两半：想开箱必须两人同时在场—— 对账时能验、平时谁也偷看不了；不用保险箱，商店也不用改任何东西。

✓ 隐私和计费两头都占

注：TEE 在"相信芯片没问题"的前提下是可行的，区别是信任转移而非消除； DECO 的"△"指查询内容对证人只能有限隐藏——它保护的是来源，不是查询内容。

Phase 1 · 三方打招呼

第一步：配出一把"两半的钥匙"，招牌还是我自己验

跑腿的本质上只算"半个顾客"：和商店换钥匙时，他那半把只分到他手里， 整把钥匙从头到尾不存在于任何地方。 商店递过来的"营业执照"也只在我这边拆开看—— 他想冒名顶替成别的商店，门都没有。

A → R → S
打招呼：各自出一半原料
我出 Z_A、跑腿出 Z_R，拼成一次性的"接头暗号"key_share 发给商店 （ECDHE：CKS = Z_A + Z_R）
A ⇄ R · 合力计算
两半钥匙在这里锻出来
每人只拿到自己那半把钥匙材料，合力算出整串钥匙——但谁也没见过整把 （ECtF 点加 → HKDF 链，全程 2PC）
S → R → A
商店递来上锁的"营业执照信封"
由我拆开：店名对不对、章对不对——跑腿的根本打不开 （crt/CV/SF 由 A 本地解密验证）
A ⇄ R · 合力计算
对账用的那半把钥匙留下来，并立字据
跑腿的留下半把"账单钥匙"份额，我把自己的半把盖章封存（com_A），以后想耍赖换把钥匙也不行 （com_A = H(tk_A∥r)）
A → R → S
回执：通道开通
我写好回执、跑腿的跑腿——商店收到一份完全正常的答复，开始营业 （Client Finished）
✗ 偷换商店实测：跑腿的把我们带去 api2.evil.com → 我这头执照店名不对，当场走人（已测试）。

Phase 2 · 填购物单

第二步：单子拼好上锁——连"哪一段有多长"跑腿的都猜不到

单子是拼起来的：有的格子大家都知道（表头），有的格子只有我知道 （数量），还有的格子连"有多长"都是秘密（地址写了几个字）—— 接缝全部抹平，装进上锁的信封。

P 表头·大家都看得到 Af 定长·只有我知道 As 变长·连长度都是秘密 自动算出来的"包裹重量"字段

能直接拼的就直接拼

大家都知道的表头部分本地拼上，不用商量，零成本 （Π_LDC）。

有秘密的格子"盲着"拼

把带秘密的段像转盘子一样错位再合并，缝在哪、多长全看不出 （SHC 结构隐藏拼接， blind_rotate）。

整单上锁+防拆封

两半钥匙一起转、单子封死上蜡，跑腿的原样递给商店 （2PC-AEAD：tk = tk_A ⊕ tk_R）。

Phase 3 · 对账单

第三步：撕一条缝，只核那一行数字

账单（商店回的信封）我不能自己拆了报数——跑腿的不信。 于是两人合力只在账单上撕开一小条缝，露出收钱那一行， 隔着信封核对：是这行、是这个数、层级也没错。

只撕最省的一条缝

离信封头近就从前往后数、离尾近就从后往前数， 选短的那头——几百字节的信也只验要用的那几块 （边界窗口 ω=(o,ℓ,ρ)）。

信封里跑一台"对账小机器"

引号里的花括号、转义符都不算数——保证核对的是真字段而不是样子像的字符 （JSON 解析 FSM：串/转义/深度）。

我的半把钥匙早就封存了

事先盖章存过指纹，想换把"更好说话"的钥匙来解释信封？门都没有 （com_A = H(tk_A∥r) 重检）。

跑腿的最后只得到一个字

"对得上"还是"对不上"——一个比特，账单其它内容依旧谁也看不见 （accept = com_ok ∧ bytes_ok ∧ depth_ok）。
